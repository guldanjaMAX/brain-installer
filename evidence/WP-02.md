# WP-02: WhatsApp export parser — evidence

## What was built

- `ingest/whatsapp-export.mjs` (new): detection (`detectWhatsAppExport`),
  the date-format disambiguator (`resolveDateFormat`, `tryReading`), the
  per-message parser (`parseWhatsAppExport`), and thread-title derivation
  (`deriveThreadTitle`). Handles both the iOS bracketed layout
  (`[3/4/26, 10:15:32 AM] Name: text`) and the Android unbracketed layout
  (`3/4/26, 10:15 - Name: text`), 12h and 24h clocks, media placeholders,
  deletions, and system/group notices (skipped, not documented).
- `ingest/run.mjs`: `prepare()` now content-sniffs every `.txt` file (not
  merely by extension — most `.txt` files are not exports) and, when one
  matches, routes to a new `prepareWhatsAppExport()` that sessionizes the
  whole file through the existing `ingest/message-session.mjs`
  (`MessageSessionizer`) and returns `{ hash, envelopes: [...] }` — many
  documents from one file — instead of the usual single `{ hash, envelope }`.
  Everything else (PDFs, .docx, plain text that is not an export, etc.) is
  completely unaffected.
- `brain.mjs` `cmdIngest`'s `prepareOne`: widened to accept a `prepare()`
  result carrying `envelopes` (plural) as well as the existing `envelope`
  (singular), keyed on the file's own path since a multi-document family has
  no single envelope identity to key state on. Reuses every existing
  mechanism unchanged — `batchStream`'s existing per-envelope unwrapping,
  the family-plan reconciliation used for `splitOversized`, the credential
  scanner, local skip/unchanged state — nothing new was invented for
  batching or resume; this only widens what "one prepared unit" is allowed
  to mean. One refused envelope in a family refuses the whole file rather
  than partially loading it, matching the credential gate's existing
  all-or-nothing posture elsewhere.

## The date-disambiguation policy, exactly as specified

Per-message day/month cannot always be told apart from range alone (`3/4/26`
is valid as either March 4th or April 3rd). The resolver tries reading every
date in the file as D/M and as M/D, keeps whichever produces a
**non-decreasing timestamp sequence across the whole file** (a chat is
inherently chronological), and:

- resolves immediately if only one reading is even calendar-valid (a "month"
  over 12 fails outright);
- resolves via pure chronological ordering when every value is individually
  ambiguous (1-12) but only one reading stays in order across month
  boundaries;
- refuses to guess and flags the file when **both** readings stay
  internally consistent (the chat is too short or too regular to tell) or
  **neither** does (something else is wrong), rather than picking one.

## The real CLI, exercised end to end via `--dry-run` (no live infra needed)

`--dry-run` never resolves a Cloudflare account or admin key, so this ran
against the actual `brain.mjs` CLI, unmodified, with a throwaway copy of
`templates/brain.manifest.json`, no fabricated output:

8 = 2 sessions from `android-unambiguous.txt` (Feb 14 + Feb 15, split by the
day/6-hour-gap boundary) + 2 from `ios-unambiguous.txt` (Jan 13 + Jan 14) + 4

excluded with the exact refusal reason, not silently mis-dated. This is the
plan's own acceptance line — "`brain ingest --from documents` ... on a
fixture folder produces sessionized documents" — proven for real.

## What was NOT verified, and why

- **"A question about fixture content returns a cited answer"** requires a
  live deployed brain (Cloudflare account, `brain provision`, `brain
  deploy`) to actually send documents and then `brain ask`. This session has
  no live Cloudflare credentials for a throwaway test account, the same
  constraint named for WP-01 and WP-04's live-calendar half. The dry-run
  proof above establishes that the correct documents WOULD be sent, with the
  correct content and dates; it does not establish server-side retrieval.
- `--from whatsapp-export` was not added as a separate CLI flag. The plan
  offered `--from documents` or a dedicated `--from whatsapp-export` flag
  "if cleaner"; content-sniffing inside the existing local `--path` walk
  turned out to be cleaner still — it needed no new flag, no new command,
  and no duplication of the walk/state/batching/credential-scanner
  machinery `cmdIngest` already has, and it means a client's mixed export
  folder (WhatsApp exports next to PDFs and leases) just works in one
  `brain ingest <manifest> --path <folder>` run.
- `.zip` exports (chat plus media) are out of scope for this pass, stated
  in `ingest/whatsapp-export.mjs`'s own header comment. A `.zip` is refused
  by the normal extension gate today, not silently misread; unpacking one to
  find the `_chat.txt` inside is a natural follow-up, not done here.
- No live server round trip means `brain sources`/`brain forget --source
  <name> --dry-run` were not exercised against a real WhatsApp-sourced
  document family; those commands themselves are unmodified by this
  package and already covered by existing tests.
