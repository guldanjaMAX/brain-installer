# WP-04: Calendar verification and matrix truth pass — evidence

## The central finding, and why this package's scope grew

The plan's premise for WP-04 was "the code says Calendar is built; the
matrix says 'designed, not written.' Make the documentation true." Verifying
that meant first finding out which of the two was actually true. Neither
was.

```
$ grep -rn "syncAll\|syncCalendar\|google-calendar" --include="*.mjs" . \
    | grep -v "node_modules\|connectors/google-calendar.mjs\|test/google-calendar.test.mjs"
(no output)
```

`connectors/google-calendar.mjs` is a fully built, carefully documented,
223-test-covered connector. Nothing anywhere in the repository ever called
`syncAll()` or `ingestEnvelopes()` outside its own test file. `brain connect
google --scopes calendar` could request the OAuth scope
(`brain.mjs:cmdConnect`'s usage string literally lists `calendar` as a valid
scope name), but there was no subsequent command — `brain ingest --from
calendar` did not exist; `cmdIngestRemote`'s allowlist was `["drive",
"gmail"]` only. Running the command the requirements doc assumed existed
would have died immediately with "not a source. Available: drive, gmail."

This is a different, and more confusing, failure mode than either "built" or
"designed, not written" — the work was done and tested in isolation, and
then never connected to anything a person could actually run. Verifying it
was therefore impossible without first building the missing entry point, so
that is what this package did, beyond its original "verification" framing.
This is flagged explicitly per the instruction to report when a package
turns out bigger than scoped, rather than silently expanding it.

## What was built

- `brain.mjs`: new `cmdIngestCalendar(m, manifestPath, flags, options)`,
  wired as `brain ingest <manifest> --from calendar [--dry-run] [--reset]
  [--source <name>]`. Deliberately its own function rather than a third
  branch inside `cmdIngestRemote`: the calendar connector already carries
  its own complete sync-then-send pipeline (`syncAll` returns finished
  envelopes AND deletions in one pass; `ingestEnvelopes` sends them one at a
  time so a single refused event never aborts the rest). Bolting that onto
  `cmdIngestRemote`'s `batchStream`/family-plan machinery — built for files
  that must be split and re-batched — would have risked the well-tested
  Drive and Gmail paths for no real gain. Reuses what fits
  (`postSourceReceipt` for `brain sources` visibility, `applyDriveRemovals`
  for cancelled-event cleanup, `googleAuth("calendar")` for the token, which
  already returns the exact plain-function shape `syncAll` expects); writes
  new code only for what was actually missing (a small sync-token state file
  reader/writer, since the existing `ingest/run.mjs` `loadState` resets to
  the wrong shape for anything without a `.done` key).
- `cmdIngestCalendar` accepts an `options` object for every external
  dependency (`resolveAccount`, `resolveBaseUrl`, `resolveAdminKey`,
  `getAccessToken`, `fetchImpl`, `postSourceReceipt`, `applyDriveRemovals`,
  `loadCalendarState`/`saveCalendarState`, and the `googleCalendar` module
  itself), matching the existing DI convention used throughout `brain.mjs`
  for `cmdUpgrade`/`cmdRollback`/`cmdDoctorRepair`. This is what makes real
  testing possible without live credentials.
- CLI help banner and `cmdConnect`'s usage string updated to mention
  `calendar` alongside `drive,gmail`.

This proves, for real: a fetched event correctly becomes an upsert
envelope; a cancelled event is correctly forwarded to removal instead of
upsert; the stored row, cancellation target, lifecycle receipt, and resume
state use one exact default or operator-selected source namespace; the sync
token is genuinely persisted to disk and genuinely reused
on the next call (the second run's outgoing request was inspected and
confirmed to carry `syncToken=TOK_1`, proving real incremental resume, not
a re-declared full sync); a dead refresh token makes a partial preview fail
closed with the exact reconnect action rather than presenting zero events as a
successful read. The latest cases also force an event send failure, a credential
refusal, and pending cancellation cleanup. Each closes the source receipt as
incomplete and withholds the new Google token; the accepted retry re-reads the
same unsaved window and only then persists its replacement token.

## The real CLI, reaching the real (and correct) boundary

This machine already has a Google connection stored from earlier, real work
on this project (scope: `drive` only) — not fabricated for this test.
Running the actual new command against it:

```
$ node brain.mjs ingest /tmp/wp02-manifest-test/brain.manifest.json --from calendar --dry-run
fail  the stored Google connection does not include the "calendar" scope (it has: drive).
  Reconnect with: brain connect google --scopes drive,calendar
$ echo $?
1
```

This is the exact correct behavior: the command exists now, is reachable,
and fails at precisely the real boundary (missing OAuth scope) rather than
at "no such command." Nothing further was attempted past this point —
adding the `calendar` scope requires the interactive Google consent screen,
which this session cannot drive, the same constraint already established
for WP-01.

## Exact command for the owner

```bash
# One time, interactive (opens a browser consent screen):
brain connect google --scopes drive,gmail,calendar

# Preview:
brain ingest <manifest> --from calendar --dry-run

# Then for real:
brain ingest <manifest> --from calendar

# Confirm it landed:
brain sources <manifest>
brain ask <manifest>   # ask something only a real calendar event would answer
```

## What was NOT done, and why

- The real, live calendar sync against the owner's actual calendar was not run,
  for the same reason as WP-01: this session cannot perform interactive
  Google OAuth consent. The exact commands are above, and the CLI path was
  proven to reach the correct real boundary given this machine's actual
  stored auth state.
- No manifest schema change was made for per-client calendar configuration
  (which calendars, event-type filters, etc.). `normalizeConfig` already
  defaults sensibly to `["primary"]` with no manifest changes required, and
  a manifest-level `calendar: {...}` block works today by simply being
  present — documenting the full configuration surface in
  `manifest.schema.json` is a reasonable follow-up, not done here since it
  was not blocking and not asked for.
