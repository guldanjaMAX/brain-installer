## 2026-08-29 common-contract hardening

## Why this package exists

The iMessage connector shipped in WP-06 needs a Mac, permanently, because
Apple only exposes message history to a local process through `chat.db` and
`chat.db` exists on macOS and nowhere else. For an owner without a Mac, WP-06
delivers nothing at all. This is the only path by which that owner's iMessage
and SMS history reaches their brain. A real install is imminent and the
device platform is still unconfirmed, so this is the hedge that makes the
install work either way.

## What it is, stated the way the product states it

A **one-time history load**. A point-in-time snapshot of one backup, not a
connection. Nothing new arrives after the load; a message sent one minute
after the backup was taken is not in it. Bringing history forward means
taking a fresh backup and loading again. The CLI says this twice in its own
output and the matrix says it in the summary row, because "iMessage: built"
read by a client who then gets a snapshot is precisely the week-three
conversation the honesty rules exist to prevent.

## What was REUSED from the live Mac connector, and what was not

The point of reusing rather than re-implementing is that a conversation
loaded from a Windows machine and the same conversation captured live on a
Mac have to produce the *same document*, keyed the same way, or the second
one to arrive duplicates the first instead of landing as unchanged.

Imported directly from `connectors/imessage.mjs`, one import statement, no
copies:

| Reused | What it carries |
|---|---|
| `fetchMessagesSince` | The single chat.db query: the message/handle/chat/chat_message_join/chat_handle_join join, the `CAST(m.date AS REAL)` that keeps nanosecond integers inside JavaScript's safe range, ROWID ordering. |
| `rowToSessionRow` | The row-to-session mapping, and with it **`parseAttributedBody`** (the typedstream parser, all three length-prefix branches), **`macAbsoluteToIso`** (the seconds-vs-nanoseconds Apple epoch conversion), and **`platformOf`** (iMessage-vs-SMS off `handle.service`). |
| `IMESSAGE_PAGE_SIZE` | The page size, so both paths scan in the same unit. |
| `MessageSessionizer` (from `ingest/message-session.mjs`) | The shared sessionizer every chat platform uses. |

Deliberately NOT reused, with the reason:

- **`probeChatDb` / `openChatDbReadOnly`.** Their entire vocabulary is macOS
  Full Disk Access — `full_disk_access_denied`, TCC, the FDA remediation
  steps. On Windows, reporting a missing backup file as a Full Disk Access
  problem would send an owner to a System Settings pane that does not exist
  on their machine. The backup loader has its own named refusals
  (`backup_encrypted`, `backup_legacy_format`, `sms_db_not_in_backup`,
  `sms_db_file_missing`, and six more) covering the failures a backup
  actually has. The open path is also genuinely different: it copies the
  main file **plus the WAL sidecars** and opens the copy read-write so SQLite
  can replay the log, which the live path does not need.
- **`loadCaptureState` / `saveCaptureState` / the ROWID watermark.** A
  snapshot has no "since last time". There is no state file at all. The whole
  backup is re-read on every run, which is safe because documents are keyed
  by first-message GUID, so a second run lands as `unchanged`.
- **`finishStaleSessions`.** A backup is finished history; nothing can arrive
  later to extend the last conversation, so `sessionizer.finish()` closes
  every session outright rather than sweeping dormant ones on a timer.

Nothing was duplicated. There is no second copy of the typedstream parser, the
epoch conversion, the service classification or the chat.db query anywhere in
this package.

## The two assertions worth defending

**1. `Manifest.db` is queried, not a path guessed.** In every backup since
iOS 10 the files are stored under a content-addressed 40-hex `fileID`, and
the *convention* is that the fileID is `SHA-1("HomeDomain-Library/SMS/
sms.db")`. A loader could compute that and usually be right. The fixture
deliberately stores `sms.db` under a fileID that is **not** that hash, and
the test asserts the conventional path is genuinely absent from the folder:

```
PASS  the fixture deliberately stores sms.db under a NON-conventional fileID
PASS  the conventional SHA-1 path is genuinely absent, so guessing cannot work here
PASS  the loader still finds sms.db, which it can only have done by querying Manifest.db
```

Three decoy rows sit in front of the real one in the `Files` table, including
a `flags = 2` **directory** row for `HomeDomain/Library/SMS` — which shares
the domain and the path prefix — and a `MediaDomain` row. Each is asserted
not to be returned.

**2. The backup path and the live Mac path produce the same documents.** Not
"look similar" — deep equality. The same synthetic database is driven a second
time through `connectors/imessage.mjs` directly (`fetchMessagesSince` →
`rowToSessionRow` → `MessageSessionizer`) and the two envelope sets are
`JSON.stringify`-compared field for field, with a companion assertion that the
comparison is not vacuous (two real documents on each side):

```
PASS  the backup load produces the SAME documents the live Mac connector produces, field for field
PASS  that identity is not vacuous: real documents were compared on both sides
PASS  the document identity keys match, so a Mac capture of the same thread lands as unchanged rather than duplicated
```

## The WAL finding, which is the reason this took an extra pass

iOS runs `sms.db` in WAL mode, and a backup carries `sms.db-wal` as its own
separately indexed file. Opening the main file alone does not error — it
silently returns history as of the last checkpoint and **drops the newest
messages**, which are the exact ones an owner checks first to decide whether
the load worked.

This is proven by contradiction rather than asserted. The fixture checkpoints
the older messages into the main file and leaves the two newest in an
uncheckpointed sidecar. Opening the main file alone yields 6 rows; the loader
yields 8:

```
PASS  the write-ahead-log sidecar is located through Manifest.db as its own indexed file
PASS  opening the main file alone would have silently dropped the newest messages
PASS  with the sidecar replayed, the newest messages are present
PASS  the replay happens on a copy: the backup's own files are never written to
```

Replaying a WAL means writing, so the trio is copied into an owner-only temp
directory and opened there. The owner's backup is never written to. The last
assertion above checks the source file's bytes are unchanged after the load.

## The encrypted refusal

Encryption is detected twice, independently. Apple's own `IsEncrypted` flag
in `Manifest.plist` is the first check. The second is `Manifest.db`'s own
bytes: an encrypted backup encrypts its index too, so the file is not a
SQLite database. The test flips the plist flag back to `false` on the second
fixture so **only** the byte check can catch it.

The second check deliberately does not overclaim. A damaged `Manifest.db`
looks identical from outside, and the message says so ("this cannot tell the
two apart from here") rather than telling an owner their backup is corrupt
when it is merely encrypted.

The refusal states the cost of the fix, not only the fix: an unencrypted
backup is readable by anything else on that computer, and health data and
saved passwords only ride along in an encrypted one. That is asserted, not
just written:

```
PASS  Apple's own IsEncrypted flag refuses the backup by name
PASS  the refusal explains WHY it cannot proceed: the index itself is encrypted
PASS  the refusal gives the exact steps to make an unencrypted backup, on BOTH operating systems
PASS  the refusal states the cost of turning encryption off rather than only the benefit
PASS  locating the Messages database in an encrypted backup throws IphoneBackupError, not an SQLite parse error
PASS  a Manifest.db that is not a SQLite file is caught even when the plist claims unencrypted
PASS  that second check does not overclaim: it says it cannot tell encrypted from damaged
```

## What is genuinely unprovable without a real iPhone backup

Stated plainly, because a matrix that overclaims costs more than one that
admits a gap:

1. **No backup Apple itself wrote has ever been through this.** Every fixture
   in the test suite is written by the test. Real backups differ in ways a
   synthetic one cannot anticipate: a real `Info.plist` embeds every installed
   app's icon and runs to tens of megabytes (which is why the plist reader
   decodes only the keys asked for), a real `Manifest.db` holds tens of
   thousands of `Files` rows, and a real `sms.db` is hundreds of megabytes with
   years of history. Nothing here proves behaviour at that scale.
2. **No genuinely encrypted backup has been through this.** The two encrypted
   cases are Apple's own `IsEncrypted` flag and a `Manifest.db` that is not a
   SQLite file. Those are what encryption looks like from the outside, which is
   all this loader ever needs to know, but a real encrypted backup was not used.
3. **No real Windows machine has run this.** The Windows path handling is
   proven by construction — `node:path` composition asserted against the three
   product layouts, source scanned for shell-outs and POSIX literals — on a
   macOS host. `%APPDATA%` expansion, drive letters, long-path behaviour and
   Windows file locking during the WAL copy are all unexercised. This is the
   single largest gap and it is the one that matters most, since running on
   Windows is the entire reason the package exists.
4. **No real ingest endpoint.** The batch push, the receipts and the credential
   gate are faked in test. The command routes through the same shared
   `requestIngestBatch` every other connector uses, so the gate applies by
   construction, but that was not observed against a live worker.
5. **`brain forget` end to end.** The worker's `forget()` is exercised for real
   against the real migrated schema. The CLI `cmdForget` around it reads live
   Cloudflare account state through `process.argv` and was not driven; only the
   deletion it calls was.
6. **Scale and timing.** No performance claim is made anywhere. Page size,
   memory behaviour on a multi-gigabyte backup, and how long a real load takes
   are all unmeasured.

## What I did not do, deliberately

- **No version bump and no CHANGELOG heading.** Three packages are in flight on
  sibling branches and all three touch those files; the owner-voice paragraph
  is below for the integrator to fold into one release entry.
- **No `imessage-exporter` evaluation.** The plan offered it as an alternative
  to a direct Manifest.db/sms.db parse. It is a third-party Rust binary that
  would have to be shipped, version-pinned and trusted per platform, and it
  would have meant a second, drifting implementation of extraction logic this
  repo already owns. Reusing the live connector's own functions was both less
  code and the only way to get document identity between the two paths.
- **No decryption of encrypted backups.** That is a genuinely separate piece of
  software (class keys, the keybag, per-file protection classes). Half-doing it
  would mean failing with an SQLite parse error on a file that is not corrupt.
  Refusing with the exact steps to make an unencrypted backup is the honest
  version, and it is what shipped.
- **No attachment reading and no contact-name resolution.** Both are named as
  absent in the matrix rather than quietly missing.
- **No live capture on any OS.** Out of scope by definition; the matrix says the
  Mac connector is the only thing that keeps up with an ongoing conversation.

> **Your iPhone messages, without needing a Mac.** If your business runs on
> Windows, the iMessage connector could not help you — Apple only opens that
> door on a Mac, and no amount of engineering changes that. So there is now a

> It finds the backup on its own, reads your iMessage and text history out of
> it, and loads it the same way everything else loads: as a named source you

> encrypted the load will stop and tell you exactly how to make an unencrypted
> one, including the two things worth knowing before you do.
