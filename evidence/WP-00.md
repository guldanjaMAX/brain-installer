## Diagnosis (read before writing any fix, per the plan's instruction)

Read in full before touching code: `doctor.mjs`, `brain.mjs` `cmdMigrate`
(migration application + restart-safe statement runner), `cmdUpgrade` (the
full snapshot/migrate/deploy/verify state machine and its stage-by-stage
`die()` messages), `cmdRollback`, `cmdStatus`, `cmdDoctor`, and
`worker/src/index.js`'s `/health` route.

**What is NOT the root cause.** The migrations themselves (0010-0013, the
ones that gate the paused-worker cutover) are already restart-safe by
construction:

- `runRestartSafeMigrationStatements` (brain.mjs) inspects `PRAGMA
  table_info` before any `ALTER TABLE ... ADD COLUMN` and skips it if an
  identical column already exists, so a statement that partially landed
  before a crash is not re-run destructively.
- Every `CREATE TABLE` / `CREATE INDEX` / `CREATE TRIGGER` in migrations
  0010-0013 uses `IF NOT EXISTS`, and every `DROP TRIGGER` before a
  recreate uses `IF EXISTS`.
- The `UPDATE install_state ...` seed statements are self-guarding (e.g.
  0012's backfill only fires `WHERE ... vector_projection_bootstrap_epoch =
  0 AND vector_projection_bootstrap_cursor IS NULL`, which becomes false
  after the first successful run).
- `cmdUpgrade` itself is proven idempotent and fail-closed at every stage by
  the existing `test/upgrade-verify.test.mjs` (154 assertions, unmodified by
  this change) — a migration failure leaves the compatibility Worker paused,
  commits nothing, and preserves the D1 recovery bookmark in its error
  message.

**What IS the root cause.** The gap is entirely in what a human (or the
collaborator) could actually do about the stuck state, not in whether a
retry would work:

1. `brain doctor <manifest>` — the one command whose whole job is telling an
   operator what is wrong — never asked the DEPLOYED brain about its own
   live state. It only ever ran the local-machine preflight checks (Node,
   network, Cloudflare token, Vectorize reachability, Google connection).
   `grep -n "accepting_documents" brain.mjs` before this change matched
   nothing outside a single die()-message string; the field 0.1.19 added to
   `/health` was never read back by any CLI code path.
2. `brain health <manifest>` DOES surface `accepting_documents: false` in
   its raw JSON dump today, but only as one line inside a larger text blob
   it never interprets — nothing marks it as the headline fact, and the
   command goes on to report the authenticated documents endpoint as
   reachable (reads are not paused), which reads as "basically fine."
3. There was no dedicated repair/resume command at all — only the general
   instruction inside the upgrade failure message ("Safe default: fix the
   reported issue and run brain update again"), which requires the operator
   to already understand that a bare re-run is safe, and gives no way to
   see the exact stage, elapsed time, or bookmark without separately
   querying `upgrade_runs` by hand.

**Effort:** landed within the plan's 2-4 day estimate; no expansion needed
because the underlying resume mechanism (`cmdUpgrade` re-entry) already
existed and was already safe — the work was giving it a named, precise,
diagnosis-first entry point, not re-engineering migration safety.

## What was built

- `probeUpgradePause(manifestPath, options)` — read-only, tolerant probe of
  a deployed brain's `/health`. Works without a Cloudflare token whenever
  `brain.domain` is set (the common case for an already-installed brain);
  degrades to `{checked:false, reason}` on any failure, never throws.
- `diagnoseStuckUpgrade(manifestPath, options)` — layers the exact stage
  (parsed from `upgrade_runs.detail`), the D1 recovery bookmark, from/to
  version, and elapsed pause time on top of the probe. A D1 outage degrades
  the enrichment, never hides the headline pause fact the `/health` probe
  already proved.
- `brain doctor <manifest>` now runs the probe as an additional check and
  fails (not warns) if the brain is paused, with a fix pointing at
  `--repair`/`--rollback`.
- `brain doctor <manifest> --repair [--yes]` — prints the full diagnosis,
  previews with no `--yes`, and on `--yes` replays `cmdUpgrade` (the same
  path `brain update` runs), which resumes from wherever it stopped.
- `brain doctor <manifest> --rollback [--yes]` — same diagnosis, then
  restores D1 to the bookmark read straight out of `upgrade_runs` (no more
  copying it by hand out of a die() message). Refuses if no bookmark is on
  record, rather than guessing one.

## The collaborator's own install: diagnosed, NOT live-repaired, and why

The plan's acceptance line reads: "the collaborator's install accepts
documents again, verified live." That step was **not performed**, and is the
one part of WP-00 this session did not complete. Here is exactly why, so this
is not silently reported as done:

- This machine has no manifest, D1 database id, or Cloudflare API token for
  the collaborator's real production install. A filesystem search
  (`find /Users/operator -iname "*collaborator-brain*"` and equivalents) found
  none. The only local collaborator-related brain artifact is
  `~/Documents/Home stuff/Financial Brain Collaborator Preview/brain.manifest.json`,
  which is a separate, already-healthy PREVIEW instance — confirmed live via
  the `financial-brain-collaborator-preview` MCP's `brain_health` tool, which
  returned `vector_readiness.ready: true` and no `accepting_documents`
  field at all (i.e. this is not the paused install described in the plan).
- Per the plan's own Section 0 rule 4 ("Client-owned, always... Tokens live in
  the client's Keychain... No Financial Brain infrastructure ever holds client
  data or credentials"), the credential needed to run `brain doctor <the
  collaborator's manifest> --repair --yes` against his real worker is not
  something this build session should hold or be handed silently. It belongs
  to the collaborator and the owner, entered interactively.
- Mutating a real client's production D1 and Worker is exactly the class of
  action this environment's rules require a human to actually perform,
  parallel to the OAuth constraint already called out for WP-01 and WP-04:
  prepare the exact commands, do not fabricate having run them.

**Exact commands for the owner (or the collaborator) to run**, once the
collaborator's real `brain.manifest.json` and a Cloudflare API token scoped to
his account are available, using the code built in this commit (after this
branch merges and `npm install`/`npx wrangler` picks it up, or directly
against this worktree with `node brain.mjs ...`):

```bash

# This alone should now show a FAIL line for "upgrade state" instead of
# silence, with the exact stage, elapsed pause time, and D1 bookmark, if the

# 2. Preview the repair (still nothing changes):
```

```bash

```

which restores D1 to the bookmark captured just before the failed
migration, then requires the supervised Vectorize-index recreation
`cmdRollback` already warns about before the brain returns to active use
(unchanged, pre-existing behavior — this package did not touch that
recovery procedure, only how the bookmark is found).
