## The VTT parser: which one was ported, and why it matters

The brief said to port `vttToPlainTranscript` from the reference's
reconciliation lib rather than `parseVTTTranscript`, which is the one actually
live on the reference's ingest path, because the live one never strips WebVTT
cue-number lines. **Both reference functions were read first-hand in
`~/CloudflareWorkers/meeting-notes` (read-only; nothing there was modified),
and the claim is confirmed**: `parseVTTTranscript`'s speaker regex requires a
colon, so a bare cue number like `2` never matches it and falls through to
`currentText += " " + trimmed`.

Porting was not a copy. Three further faults were found in the better
reference parser while porting, and all four are fixed with a fixture each.
The demonstration below runs verbatim copies of BOTH reference parsers and the
ported one over the four shipped fixtures:

```

Priya Nair: No problem at all. I pulled the renewal numbers you asked for. 3
Priya Nair: They are a little better than last quarter, about four percent up. 4
Alex Rivera: Good. Send them over and I will read them before Thursday.
```

What that output shows, fault by fault:

1. **Cue numbers leak** (`cue-numbers.vtt`). The live reference parser appends
   `2`, `3`, `4` into the transcript text. This is the bug the brief named.
   Ported output is clean.
2. **Header metadata becomes a speaker** (`header-and-note.vtt`). Both
   reference parsers turn `Kind: captions` and `Language: en-US` into content;
   the reconcile one additionally attributes the NOTE disclaimer to a real
   participant, putting words in a named person's mouth. The port skips the
   header block whole and skips NOTE blocks per the WebVTT spec.
3. **A colon in a continuation line invents a speaker**
   (`multi-line-cue.vtt`). `meet at 3:30` becomes speaker `meet at 3` in the
   reconcile parser and `3: 30` in the live one. The port only looks for a
   speaker prefix on the FIRST line of a cue, so `3:30` survives as a time.
4. **An unattributed transcript parses to the empty string**
   (`unattributed.vtt`). The reference reconcile parser returns `""` —
   silent, total data loss with no error anywhere. The port emits the text
   unattributed.

Fault 4 is the reason a straight port would have been the wrong call: the
"better" parser fails worse than the buggy one on that input.

## A second latent trap found while porting: the timestamp's unit

The reference's replay guard treats `x-zm-request-timestamp` as epoch
milliseconds, asserted in a code comment. That may be right. It is not
verifiable here, and it is not a safe thing to inherit on faith, because the
failure mode is asymmetric:

- If the unit is milliseconds and we assume seconds, or vice versa, every real
  event lands ~55 years outside a five-minute window and is refused with a 401
  that looks exactly like an attacker being turned away.
- The reference can absorb that. It also runs a 15-minute cron that sweeps for
  recordings, so a webhook rejecting 100% of deliveries would be silently
  covered by the poll and might never be noticed.
- **This connector is webhook-only by design.** The same mistake here is total
  silent failure with nothing behind it: no transcripts, ever, and a 401 in a
  log nobody reads.

So `zoomTimestampToMs` accepts both units. `1e11` separates any plausible
epoch-seconds value (~1.8e9 today) from any plausible epoch-milliseconds one
(~1.8e12). This widens only the REPLAY window; the signature is still computed
over the header's exact original characters, because those are what Zoom
signed. Normalizing before hashing would break every signature, and there is a
test asserting the seconds path still refuses a six-minute-old body, so the
tolerance did not buy leniency.

This is defensive, not a claim to know the answer. The unit remains on the
unprovable list below.

## A third guard added for the same reason: secret propagation

`connect` writes the four secrets and then immediately asks the live worker to
answer Zoom's challenge. A secret written seconds ago does not always reach an
already-running isolate, so a single check can answer with the PREVIOUS secret.
That failure is indistinguishable, from the client's side, from having copied
the wrong Secret Token — and acting on it means going back to Zoom to re-copy a
value that was already correct.

The check is therefore retried up to three times with a short wait, the retry
is printed rather than hidden, and a genuinely wrong secret still fails after a
bounded number of tries. Both behaviours are tested: `a secret that lands on
the second check still connects` and `a genuinely wrong secret still fails,
after a bounded number of tries`.

## Decisions taken (scope narrowing, as the brief directed)

- **Webhook-only, no sweep.** The reference runs a webhook AND a 15-minute
  cron against the same recordings, which is why it needs a poll-style
  backlog processor and a bespoke claim-row table with a 30-minute TTL. There
  is no cron here. The webhook names the exact recording, so the handler
  fetches that one and writes one document, and the brain's existing
  `(source_type, source_id)` plus content-hash idempotency makes a redelivered
  webhook a no-op for free. No dedupe table was ported or written.
- **`recording.transcript_completed`, never `recording.completed`.** The audio
  file is written before the VTT is.
- **The per-occurrence `uuid`, never the shared meeting id**, double
  URL-encoded in the path per Zoom's own convention. A recurring meeting
  reuses one meeting id across every occurrence; the reference carries a code
  comment about a real incident caused by that ambiguity.
- **One scope: `cloud_recording:read:admin`.** The reference's four
  `user:*`/`meeting:*` read+write scopes exist for an unrelated admin feature
  (flipping auto-recording defaults) and were not carried over.
  `user:read:admin` is offered as OPTIONAL and read-only, solely so the plan
  check can be definitive; declining it produces a named unknown, not a guess.
- **No downstream pipeline.** No LLM call analysis, no content screening, no
  Drive filing, no lead creation. A transcript becomes a searchable, citable,
  forgettable document.
- **The route is the only unauthenticated-by-key write path in the worker**,
  so it fails closed with no secret set, compares signatures in constant time,
  enforces a five-minute replay window, refuses corpus writes while an upgrade
  is paused, and runs the credential gate before the store like every other
  ingest door.
- All fixtures and test personas are invented (Alex Rivera, Priya Nair, Sam
  Osei, Jordan Lee, Morgan Diaz, plus `northwind`/`Northwind Supply` in the
  CLI test), consistent with `test/fixtures/`. No real person, client or
  organization appears anywhere in this package.

## What could NOT be proven, and why

**There is no paid Zoom account in this environment, so nothing below was
faked to look otherwise.** These are unprovable here, not skipped:

1. **The package's own acceptance criterion.** No real Zoom meeting has
   produced a cited transcript document. Not attempted, not simulated.
2. **A real signature from Zoom.** Verification is proven against HMACs
   recomputed independently with `node:crypto`, so a bug in the verifier
   cannot agree with itself — but never against bytes Zoom actually signed.
3. **Zoom's real `endpoint.url_validation` POST**, the one the Marketplace
   fires when the URL is saved. Our challenge is the same shape and the worker
   answers it, but Zoom's actual save-time validation has never run.
4. **Zoom's real VTT dialect.** The fixtures are hand-written to the WebVTT
   spec and to what the reference's parsers imply Zoom emits. A real Zoom
   transcript may carry cue identifiers, styling or speaker formats the
   fixtures do not represent. This is the most likely place the first live run
   finds something.
5. **The real `/v2/meetings/{uuid}/recordings` response**, and whether the
   double-encoded uuid behaves as documented against Zoom's live router.
6. **Whether `/v2/users/me` is readable with only
   `cloud_recording:read:admin`.** Unknown, and deliberately so: the code
   handles both outcomes and the plan check degrades to a named unknown rather
   than asserting one. Which one Zoom actually does is a live question.
7. **The transcript download** with `?access_token=` appended to Zoom's signed
   URL.
8. **Plan type values in the wild.** `1 = Basic`, `2 = Licensed`,
   `3 = On-prem` is taken from the reference's own code and comment, not
   observed here.
9. **Which unit `x-zm-request-timestamp` actually uses.** Both are accepted
   (see the section above), so this cannot break the connector either way, but
   the answer itself is unverified here.
10. **A live Cloudflare secret write.** The four-secret PUT is driven against a
   recording closure; the underlying call path is the same one `brain secrets`
   already uses in production.

### What was deliberately NOT done (scope, not omission)

- No cron, sweep or backlog processor, and therefore no claim-row dedupe
  table. Webhook-only.
- No backfill: recordings made before connecting are not loaded, ever.
- No downstream CRM pipeline (call analysis, Drive filing, lead creation).
- No participant fetch — it needs a different Zoom permission family and the
  reference's version fails soft, so it was never forced to be scoped
  correctly. Dropped rather than half-shipped.
- No write scopes requested anywhere.
- Nothing under `~/CloudflareWorkers` was modified; it was read only.
- **No `package.json` version bump and no `CHANGELOG.md` heading**, per the
  merge discipline for three parallel branches. The owner-voice paragraph is
  below for the integrator to consolidate.

## The exact live verification, for the owner to run

Everything here needs a **paid (Licensed) Zoom seat**. Steps 1 to 6 are the
real end-to-end proof; step 0 is runnable today against any deployed brain.

```bash
# 0. Provable with no Zoom account at all: the webhook fails closed and
#    refuses unsigned bodies. Run against a deployed brain.
curl -sS -o /dev/null -w '%{http_code}\n' -X POST https://<brain-domain>/api/webhooks/zoom \
  -H 'content-type: application/json' \
  --data '{"event":"recording.transcript_completed","payload":{"object":{"uuid":"x"}}}'
#    503 = no ZOOM_WEBHOOK_SECRET_TOKEN set yet (fail closed).
#    401 = secret is set and the unsigned body was refused. Both are correct.
#    A 200 here would be a bug worth stopping for.

# Prerequisites for the rest, all in the CLIENT'S own accounts:
#   - a paid (Licensed) Zoom seat
#   - Zoom Settings > Recording > Cloud recording ON, with Audio transcript ON
#   - the brain worker deployed:  node brain.mjs deploy <manifest>
#   - "zoom": { "enabled": true } under "corpora" in the manifest

# 1. Print the exact Zoom Marketplace steps (safe: writes nothing).
node brain.mjs connect zoom <manifest>

# 2. Create the Server-to-Server OAuth app, scope cloud_recording:read:admin
#    (optionally also user:read:admin), Activate it, copy the four values.
#    Supply them through the approved launcher/secret manager, never on the
#    command line, then:
node brain.mjs connect zoom <manifest>
#    Expect, in this order:
#      checking these credentials against Zoom
#      Zoom plan: Licensed. Cloud recording is available on this account.
#      Zoom credentials verified, and the recording scope is granted
#      four Zoom secrets written to <worker> in the client's own Cloudflare account
#      the brain answered Zoom's validation challenge correctly. The URL will save.
#      ...then the Event Subscription steps, with the URL.

# 3. In the Zoom app: Feature > Event Subscriptions > add the printed URL,
#    click Validate (it MUST save), add ONLY recording.transcript_completed,
#    Save, Activate.

# 4. Hold a short Zoom meeting with cloud recording on. End it. Wait for
#    Zoom's transcript to finish — typically several minutes, longer for a
#    long meeting. This lag is Zoom's.

# 5. Prove it landed.
node brain.mjs sources <manifest>     # expect a zoom row, document_count 1
node brain.mjs ask <manifest>         # ask about something said on the call;
                                      # expect a cited answer from the transcript

# 6. Prove the undo, both halves.
node brain.mjs forget <manifest> --source zoom      # removes the transcripts
node brain.mjs disconnect zoom <manifest>           # removes the four secrets;
                                                    # rerun step 0, expect 503
```

If step 3's Validate fails even though step 2 said the challenge was answered
correctly, the cause is almost certainly that the URL typed into Zoom is not
the URL step 2 printed. Step 2 already proved the worker answers correctly at
that exact URL.

## Owner-voice changelog paragraph (for the integrator to consolidate)

**Your brain can now read your Zoom calls, automatically.**

If your Zoom account is on a paid plan and records to the cloud, `brain
connect zoom <manifest>` sets up a direct line: every time Zoom finishes
writing a transcript, it tells your brain, and your brain fetches and stores
that transcript on its own. No saving files, no dragging anything into a
folder. The Zoom app, the credentials and the recordings all stay in your
account — the setup walks you through creating the app in your own Zoom, and
the four values it gives you are written as secrets on your own worker.

The honest limits, stated up front. A paid (Licensed) Zoom seat is required:
Zoom's free tier cannot record to the cloud at all, so there is nothing to
transcribe, and the setup checks your plan and refuses rather than connecting
you to silence. Only NEW recordings arrive — nothing goes back and collects
calls you recorded before connecting; for those, saving the transcript into a
Drive folder you already ingest still works. Transcripts appear a few minutes
after the call ends, on Zoom's schedule rather than instantly. And this loads
the transcript only: not the audio, not the video, and no summary of the call.
It is the named source `zoom`, so `brain sources` shows it and `brain forget
<manifest> --source zoom` takes every transcript back out. `brain disconnect
zoom <manifest>` shuts the door.

One thing worth knowing: this has been built and tested thoroughly, but it has
not yet run against a real Zoom account. You will be the first. Expect the
first call to be the one that finds anything the tests could not.
